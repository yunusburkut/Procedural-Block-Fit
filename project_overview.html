Project Overview — Technical Document

Blokfit

A tangram-style 2D puzzle game built in Unity 2D. Players arrange procedurally generated right-triangle pieces on a grid board. This document describes the complete project architecture: namespaces, system responsibilities, data flow, design patterns, and the level content pipeline.

Unity 2D C# · .NET DOTween TextMeshPro Triangular Grid Command Pattern Procedural Generation

1 — Game Concept

Blokfit is a tangram-style placement puzzle. The board is an N×N grid subdivided diagonally into right-angle triangles (2N² total). A set of irregular pieces — each itself a connected group of triangles — is scattered in a tray below the board. The player drags pieces onto the board until every triangle is covered.

  • Levels can be procedurally generated at runtime with a seed and a difficulty profile.
  • Levels can also be hand-authored in the built-in Level Editor and saved as JSON.
  • Levels can be fetched from a server (optional); the game falls back to procedural on failure.
  • Every placement is undoable through a Command-pattern history stack.

2 — Project Structure

All runtime code lives under Assets/Scripts/ and is compiled into a single assembly (Blokfit.Scripts.asmdef). Editor-only code is in a separate assembly (Blokfit.Editor.asmdef) so it is never included in builds.

Blokfit.Core

Data & Bootstrap

Level data models (LevelData, GridData, PieceJson), JSON serialisation, and the GameManager that orchestrates the full game loop.

Blokfit.Generation

Procedural Level Creation

LevelGenerator drives the pipeline. TrianglePartitioner performs the randomised BFS flood-fill on the triangle grid.

Blokfit.Board

Board State & Snap

BoardController owns the snap-point grid and triangle occupancy map. SnapSystem executes the snap-to-grid logic on piece release. SnapPoint marks each grid vertex.

Blokfit.Pieces

Piece Runtime

PieceFactory converts JSON → PieceData. PieceSpawner instantiates and animates pieces. PieceBehaviour handles rendering, collider, drag input, and snap-dot hints.

Blokfit.Input

Input Gating

InputHandler ensures exactly one piece is dragged at a time and blocks all input during non-interactive states (e.g. level-complete screen). DragState records which piece and which pointer ID are active.

Blokfit.Commands

Undo / Redo

ICommand interface with Execute() / Undo(). PlacePieceCommand is the only concrete command: it records the before/after positions and the target snap point so placement is fully reversible.

Blokfit.UI

User Interface

UIOverlay manages difficulty-select buttons, the completion panel with DOTween fade-in animations, and the "Next Level" flow. Callbacks are wired from GameManager on Awake, keeping UI and game logic decoupled.

Blokfit.LevelEditor

Editor Tool (Editor-only)

LevelEditorWindow is a custom Unity EditorWindow (Tools ▸ Blokfit ▸ Level Editor). Supports painting triangles per piece, colour assignment, and exporting LevelData JSON files.

Supporting ScriptableObjects

Blokfit.ScriptableObjects.DifficultyConfig is a Unity ScriptableObject that parameterises the procedural generator: grid size, piece count range, and piece size range. Three instances (Easy / Medium / Hard) are wired into GameManager from the Inspector.

3 — Architecture & Design Patterns

3.1 Component-based orchestration (no service locator)

Dependencies are injected through Unity's Inspector serialisation ([SerializeField] references) rather than a global service locator or singleton. GameManager is the root composition root: it holds references to every major MonoBehaviour system and wires them together during Awake / Start.

3.2 Command pattern — reversible placement

Every successful piece snap creates a PlacePieceCommand that is pushed onto GameManager's Stack<ICommand>. The Undo button pops and calls Undo() on the topmost command. The pattern cleanly separates the intent (place this piece) from the effect (board state mutation + tween), and keeps all rollback logic inside the command object.

3.3 Event-driven completion and move notification

Systems communicate upward through C# events rather than direct calls:

  • BoardController.OnBoardCompleted — fired when every triangle is occupied.
  • SnapSystem.OnMoveExecuted — fired after every successful snap with the new command.

GameManager subscribes to both and acts as the sole decision-maker about game-state transitions (Idle → LevelComplete). This prevents circular dependencies between BoardController, SnapSystem, and UI.

3.4 Factory pattern — JSON to runtime data

PieceFactory.FromJson(PieceJson, int gridSize) converts serialised absolute triangle indices into piece-local TriOffset values. The factory is a static class, has no state, and is the only place that knows the flat-index encoding scheme. Keeping this conversion logic centralised means neither the spawner nor the behaviour need to understand raw JSON.

3.5 Shared-sprite flyweight

Only two Sprite objects exist for the entire game — one for each triangle type. They are stored as static fields in PieceBehaviour. Individual triangle renderers tint using MaterialPropertyBlock to avoid per-instance material instancing. Similarly, SnapPoint uses one shared static Sprite _sharedSprite across all (N+1)² snap-point GameObjects.

4 — Full Game Loop

Application start — GameManager.Start()

The event handlers are registered (OnBoardCompleted, OnMoveExecuted) and BeginLevel(easyConfig) is called immediately to load the first level.

Level initialisation — BeginLevel(config)

The command history is cleared, the completion UI is hidden, all existing piece GameObjects are destroyed (PieceSpawner.DestroyAll()), and the board state is reset (BoardController.ResetBoard()). Then level data is obtained via one of three paths:

  • Server fetch — if _serverBaseUrl is non-empty, a coroutine downloads {url}/{difficultyName}.json and falls back to procedural on failure.
  • Procedural generation — LevelGenerator.Generate(config) runs the full pipeline and returns a LevelData object.
  • Handmade JSON — LevelSerializer.FromJson(asset.text) deserialises a TextAsset and runs ScatterSpawnPositions() to distribute pieces in the tray (since editor-exported JSONs store spawnX/Y = 0).

Scene assembly — ApplyLevel(levelData)

  1. BoardController.Initialize(N) — builds the (N+1)² snap-point grid and occupancy arrays.
  2. SnapSystem.SetSnapThreshold(cellSize) — sets the squared-distance threshold to half a cell.
  3. PieceSpawner.SpawnAll(pieces, N) — for each PieceJson:
    • calls PieceFactory.FromJson() to produce PieceData,
    • instantiates a PieceBehaviour prefab at the saved spawn position,
    • calls piece.Initialize(...) to build sprites, collider, anchor, and snap dots,
    • calls piece.AnimateIn(index) — DOTween drop-in with staggered bounce.

Player interaction loop

Unity's EventSystem routes pointer events to PieceBehaviour (which implements IPointerDownHandler, IDragHandler, IPointerUpHandler):

  • PointerDown — InputHandler.BeginDrag() is called; rejected if input is blocked or another drag is active. The board lifts the piece (BoardController.Lift()) so placed pieces can be re-dragged. Scale is boosted to 1.1× and sort order is raised above all others.
  • Drag — transform.position is updated every frame using the screen-to-world offset cached at drag-start. Camera Z is cached to avoid per-frame transform reads; a pre-allocated Vector3 buffer avoids heap allocation.
  • PointerUp — SnapSystem.TrySnap(piece) is called. On success: board is updated, DOTween snaps the piece to the exact vertex, a PlacePieceCommand is pushed to history. On failure: piece.ReturnToTray(originalPos) tweens it back.

Level completion

BoardController increments _filledTriangles on every successful placement. When it reaches _totalTriangles (N² × 2), OnBoardCompleted fires. GameManager transitions to GameState.LevelComplete, which sets InputHandler.IsBlocked = true to prevent further dragging, and calls UIOverlay.ShowCompletion() to fade in the completion panel.

Next level / difficulty change

The "Next Level" button triggers GameManager.StartNextLevel(), which re-runs BeginLevel with the same config (a new random seed is used because LevelGenerator.Generate defaults to Environment.TickCount). The difficulty buttons call BeginLevel(easyConfig), BeginLevel(mediumConfig), or BeginLevel(hardConfig) respectively.

5 — Data Model

All level data is represented as plain serialisable C# objects so Unity's JsonUtility can round-trip them without custom converters.

LevelData ├── GridData │ └── size : int // N (board is N×N cells, 2N² triangles) └── PieceJson[] ├── cells : int[] // triangle flat-indices that form the piece ├── color : string // HTML hex e.g. "#4361EE" ├── anchors : int[] // [0] = primary anchor (smallest flat index) ├── spawnX : float // tray spawn world-X └── spawnY : float // tray spawn world-Y

At load time PieceFactory converts each PieceJson to the immutable runtime representation:

PieceData ├── TriangleOffsets : TriOffset[] // piece-local relative offsets from anchor │ ├── dcol : int // Δcol from anchor cell │ ├── drow : int // Δrow from anchor cell │ └── type : int // 0 = lower ◸, 1 = upper ◿ └── Color : Color32 // parsed from hex at load time

The conversion from absolute flat indices to local TriOffset values means that once loaded, piece rendering and placement logic never need to know the board's grid size — they work purely in local (dcol, drow) coordinates.

6 — Level Content Pipeline

6.1 Procedural generation

The full procedural pipeline is documented in a companion document (Blokfit — Procedural Generation Algorithm). In brief:

  1. Initialise a seeded System.Random.
  2. Run randomised BFS flood-fill (TrianglePartitioner) to partition 2N² triangles into connected regions sized within [minPieceSize×2, maxPieceSize×2].
  3. Post-hoc merge regions until piece count ≤ maxPieces.
  4. Assign shuffled palette colour, anchor, and tray spawn position to each region.
  5. Return a LevelData value object.

6.2 Hand-authored levels — Level Editor

The Level Editor (Tools ▸ Blokfit ▸ Level Editor, shortcut Ctrl+Alt+L) is a custom EditorWindow. Its workflow:

  1. Set grid size (slider, 2–10).
  2. Create named pieces with colour pickers (10-colour auto-palette).
  3. Paint triangles by clicking the grid panel — left-click assigns to the selected piece, right-click unassigns. Clicking an already-assigned triangle toggles it off.
  4. Click ⬇ Export JSON — the editor checks for unassigned triangles (warns but does not block), builds a LevelData, serialises to JSON via LevelSerializer, and saves to a user-chosen path. If the path is inside Assets/, AssetDatabase.ImportAsset is called automatically so the file appears in the Project browser immediately.
Important Editor-exported JSON always stores spawnX = 0, spawnY = 0 for every piece. At runtime GameManager.ScatterSpawnPositions() distributes them in a circular arc around the tray center so they don't all overlap.

6.3 Server-hosted levels

If GameManager._serverBaseUrl is non-empty, a UnityWebRequest coroutine downloads {url}/{difficulty}.json and deserialises it. On any network failure (timeout, 404, parse error), the game transparently falls back to calling the procedural generator with the same config.

7 — Board & Snap System Detail

7.1 Snap-point grid

BoardController.Initialize(N) creates (N+1)² SnapPoint MonoBehaviours — one per grid vertex. Each stores its integer grid coordinates (Col, Row) and its pre-computed world-space position. Interior snap points (not on the board border) render a faint circle sprite as a visual guide; border points are invisible.

7.2 O(1) nearest-vertex lookup

Because the grid is uniform, finding the nearest vertex at drag release is a direct calculation with no search: 

int vCol = Clamp(RoundToInt((worldPos.x - boardOrigin.x) / cellSize), 0, N);
int vRow = Clamp(RoundToInt((worldPos.y - boardOrigin.y) / cellSize), 0, N);
return _snapPoints[vRow, vCol];

7.3 Occupancy tracking

Two parallel data structures keep occupancy consistent:

  • bool[N, N, 2] _occupiedTriangles — O(1) read/write for placement validation.
  • Dictionary<PieceBehaviour, List<(r,c,t)>> _pieceOccupancy — reverse map enabling O(|piece|) lift without scanning the full board.

8 — Piece Rendering

8.1 Per-triangle child GameObjects

Each triangle in a piece is represented as a child GameObject with a SpriteRenderer. Only two Sprite assets exist — one for each triangle type — generated procedurally from a 64×64 texture using a linear inequality mask (a one-pixel soft fringe is added for anti-aliasing). All triangles of the same type share the same Sprite reference; colour is applied per-instance via MaterialPropertyBlock without material instancing overhead.

8.2 PolygonCollider2D

The piece's PolygonCollider2D is assigned one path (three vertices) per triangle. This is Unity's recommended approach for concave shapes and enables EventSystem pointer hit-testing with no custom ray-cast code.

8.3 Sort order

PieceSortOrder is a global monotone counter. Each new piece claims the next integer. On drag-start, a DragSortBoost of 1000 is added to the piece's order, bringing it visually in front of all non-dragged pieces regardless of spawn order. The boost is removed on release.

9 — Input System

Input is handled entirely through Unity's EventSystem (UGUI physics raycasts + PolygonCollider2D on each piece). No Input.GetMouseButton polling is used.

9.1 Single-drag enforcement

InputHandler.BeginDrag(piece, eventData) returns false if a drag is already in progress or if IsBlocked == true. PieceBehaviour.OnPointerDown checks this return value and aborts silently if it is false. This prevents multi-touch race conditions.

9.2 Pointer ID tracking

DragState stores the PointerId that started the drag. PieceBehaviour.OnDrag verifies InputHandler.CurrentDrag.Piece == this before moving, which guards against a second touch briefly routing events to a different piece.

10 — Command Pattern & Undo

The undo system is intentionally minimal — a plain Stack<ICommand> on GameManager. There is no redo stack. The only concrete command is PlacePieceCommand, which captures:

  • The PieceBehaviour reference.
  • The BoardController reference.
  • fromPosition — world position the piece was at before the snap.
  • toPosition — world position after the snap.
  • snapPoint — the SnapPoint to re-use on Execute.

Undo calls BoardController.Lift(piece) (clears the occupancy entries) and piece.ReturnToTray(fromPosition) (queues a DOTween move). No additional state needs to be saved because the piece's triangle data is immutable.
