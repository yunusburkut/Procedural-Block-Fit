Technical Design Document

Blokfit — Procedural Generation Algorithm

A full description of the seed-based, triangular-half-cell partition system that generates puzzle levels at runtime: from grid representation through flood-fill carving, constraint enforcement, and snap-point lookup.

Blokfit · Unity 2D · C# · Namespace: Blokfit.Generation

1 — System Overview

Blokfit's levels are never hand-authored. Every time a level must be shown, a single call to LevelGenerator.Generate(DifficultyConfig, int seed) runs the full pipeline and returns a self-contained LevelData value object that can be immediately serialised to JSON or fed to the scene loader.

The pipeline has four clearly separated responsibilities:

  1. Triangular grid representation — the board is modelled as N×N×2 half-cell triangles, not squares.
  2. Randomised flood-fill partition — a BFS-based carver claims connected regions of triangles.
  3. Piece-count constraint enforcement — post-hoc merging reduces the number of regions to fit inside [minPieces, maxPieces].
  4. Metadata assignment — each region receives an anchor vertex, a shuffled colour, and a tray spawn position.

The output is deterministic: the same seed + DifficultyConfig pair always produces an identical level, enabling reproducible share-codes and server-side validation.

2 — Grid Representation: Triangular Half-Cell Encoding

2.1 Why triangles instead of squares?

A classic tangram aesthetic requires pieces that contain right-angle triangle half-cells. Modelling the board in square cells and then splitting pieces post-hoc leads to awkward mesh seams and complex adjacency logic. Instead, the board is defined as a grid of 2N² right-angle triangles right from the start — each square cell is pre-divided by a diagonal running from its bottom-left to its top-right corner (the / diagonal).

2.2 Flat index encoding

Every triangle is identified by a single integer called its flat index:

flat = (row × N + col) × 2 + type type 0 → lower triangle (vertices: BL, BR, TR) ◸ occupies lower-right half type 1 → upper triangle (vertices: BL, TR, TL) ◿ occupies upper-left half

This encoding packs a bool[] of length N²×2 as the only allocation needed for the entire assignment state. Decoding back to (col, row, type) is three cheap arithmetic operations — no hash map lookup required.

2.3 Adjacency rules

In a triangular half-cell grid each triangle has exactly three neighbours (one per edge). Lower-type triangles always neighbour upper-type triangles and vice versa:

lower(col, row) ↔ upper(col, row ) via the / diagonal (shared hypotenuse) lower(col, row) ↔ upper(col, row-1) via the bottom horizontal edge lower(col, row) ↔ upper(col+1, row ) via the right vertical edge upper(col, row) ↔ lower(col, row ) via the / diagonal upper(col, row) ↔ lower(col, row+1) via the top horizontal edge upper(col, row) ↔ lower(col-1, row ) via the left vertical edge

These six cases are the entirety of the adjacency function in TrianglePartitioner.GetFreeNeighbors. No general-purpose graph structure is needed; the rules reduce to simple column/row ± 1 checks with boundary guards.

3 — The Partition Algorithm

The partition is performed by TrianglePartitioner. Its approach is a form of randomised BFS region-growing, akin to the well-known Random BFS maze-carver but applied to create connected subgraphs instead of spanning trees.

3.1 Main loop

Find the next unassigned triangle

HasUnassigned(out int seedFlat) advances a monotone cursor (_nextSeedCursor) through the flat-index array until it finds a triangle whose _assigned[i] flag is false. Because the cursor never resets within a generation run this is amortised O(N²) total across all iterations, not O(N²) per call.

Pick a random target region size

The target triangle count is drawn uniformly from [minPieceSize × 2, maxPieceSize × 2]. Square-based sizes from DifficultyConfig are doubled because each square cell contributes two triangles.

BFS flood-fill: CarveRegion

Starting from seedFlat the carver runs a BFS, claiming neighbouring unassigned triangles until either the target size is reached or no more free neighbours exist.

At each BFS step the list of free neighbours is Fisher-Yates-shuffled with the seeded RNG before being enqueued. This randomises the shape of each piece while still guaranteeing connectivity (BFS ensures the region is always a connected subgraph of the triangle adjacency graph). 

while (queue.Count > 0 && result.Count < targetSize)
{
    int current   = queue.Dequeue();
    var neighbors = GetFreeNeighbors(current);   // ≤ 3 entries
    Shuffle(neighbors);                           // Fisher-Yates

    foreach (int nb in neighbors)
    {
        if (result.Count >= targetSize) break;
        _assigned[nb] = true;
        result.Add(nb);
        queue.Enqueue(nb);
    }
}
Performance note Both the result list (_carveResult) and the BFS queue (_carveQueue) are pre-allocated fields that are cleared rather than re-created between calls. This keeps the hot-path allocation to a single ToArray() call at the end of each region.

Immediate post-carve merge of under-size regions

If the freshly carved region is smaller than minTriSize and enough pieces already exist (count > config.minPieces), the region is folded into its nearest neighbour immediately. This prevents stray slivers from accumulating.

Repeat until the grid is fully covered

Steps 1–4 iterate until HasUnassigned returns false, guaranteeing every triangle belongs to exactly one region.

3.2 Algorithmic foundation

The approach is directly inspired by the Randomised Prim's / BFS region-growing family of algorithms used in procedural dungeon generation. The key difference from a standard spanning-tree carver is that BFS expands area rather than paths: each visited node enqueues all its free neighbours, not just one, resulting in blob-shaped, roughly convex regions. The neighbour shuffle at each dequeue step breaks the FIFO bias that would otherwise produce top-left biased rectangles.

4 — Constraint Enforcement: Post-Hoc Merging

Because flood-fill is greedy and unconstrained regarding global piece count, the result may have more regions than maxPieces allows (this is common near the grid boundary where late-stage seeds carve very small regions).

4.1 Centroid-based nearest-region lookup

All merges are guided by centroid distance. The centroid of a region is computed as the average (col, row) of its constituent triangles (using the parent square-cell coordinates of each triangle index): 

float sumX = 0, sumY = 0;
foreach (int flat in triCells)
{
    int cellFlat = flat / 2;
    sumX += cellFlat % N;   // col
    sumY += cellFlat / N;   // row
}
centroid = new Vector2(sumX / triCells.Length, sumY / triCells.Length);

Centroid values are cached in a Dictionary<int[], Vector2> keyed by array reference. When a region is merged the two stale entries are removed and the new merged array will be lazily computed on first access. This keeps repeated merges during the post-hoc phase from becoming O(N⁴).

4.2 Merge-to-max-pieces loop

while (regions.Count > config.maxPieces)
    MergeSmallestIntoNearest(regions, N);

Each iteration finds the region with the fewest triangles and merges it into its centroid-nearest neighbour. Merging the smallest region first is a greedy heuristic that tends to produce the most balanced final distribution — small satellite regions are absorbed before larger ones, keeping average piece sizes roughly uniform.

Design trade-off Nearest-centroid is not the same as nearest-touching-neighbour. In theory a merge could produce a non-contiguous region if two non-adjacent regions happen to have close centroids. In practice, on grids of size 4–8, region centroids correlate strongly with physical adjacency, and the visual result is acceptable. A fully correct approach would require maintaining an adjacency graph of regions, which was deemed unnecessary overhead.

5 — Metadata Assignment

5.1 Anchor selection

Each piece's anchor is the triangle with the smallest flat index in its region. Because flat indices increase left-to-right, bottom-to-top, this selects the bottom-left-most triangle, which keeps the anchor at a predictable and visually grounded position. The anchor's bottom-left vertex (grid vertex (col, row)) later becomes the piece's pivot in world space.

5.2 Colour palette

A fixed palette of 16 hues, spaced approximately 22° apart on the HSL colour wheel, is shuffled once per level using Fisher-Yates with the same seeded RNG. Pieces are assigned colours by palette index modulo 16. Because the shuffle is seeded, colour distribution is fully deterministic given the seed.

5.3 Tray spawn position

Each piece receives a random world-space position near the tray center, computed as: 

offset = (rng.NextDouble() * 2 - 1) * traySpread   // uniform in [-spread, +spread]
spawnPos = trayCenter + (offsetX, offsetY)

This spreads pieces slightly so they don't all start stacked, but the spread is kept small enough that all pieces remain visually inside the tray zone at puzzle start.

6 — Snap-to-Grid System

The snap system must answer one question every time the player releases a piece: "to which board vertex — if any — should this piece snap?" It is designed with two hard requirements: O(1) lookup and zero per-frame heap allocations.

6.1 Snap-point grid

At level load, BoardController.Initialize creates a 2-D array of SnapPoint objects, one per grid vertex (not per cell). An N×N cell board has (N+1)² vertices: 

_snapPoints = new SnapPoint[N+1, N+1];

for (int vRow = 0; vRow <= N; vRow++)
    for (int vCol = 0; vCol <= N; vCol++)
        _snapPoints[vRow, vCol].Initialize(vCol, vRow, GridVertexToWorld(vCol, vRow), ...);

The world position of each vertex is pre-computed once and stored directly in the SnapPoint to avoid recomputing it during the per-frame drag loop.

6.2 O(1) nearest-vertex lookup

Because the grid is regular (uniform cell size), finding the nearest vertex is a closed-form operation — no search, no spatial data structure required: 

public SnapPoint GetNearestFreeSnapPoint(Vector2 worldPos)
{
    int vCol = Clamp(RoundToInt((worldPos.x - _boardOrigin.x) / _cellSize), 0, N);
    int vRow = Clamp(RoundToInt((worldPos.y - _boardOrigin.y) / _cellSize), 0, N);
    return _snapPoints[vRow, vCol];
}

_boardOrigin (the world position of the bottom-left vertex) is cached at Initialize time so this path is four arithmetic operations and one array dereference — no branch beyond the clamps.

6.3 Threshold test and placement

Once the nearest vertex is identified, the system checks whether the piece's anchor is close enough to snap: 

float distSq = SqrMagnitude(anchorWorldPos - candidate.WorldPosition);
if (distSq >= _snapThresholdSq) return false;   // no snap

SqrMagnitude is used deliberately to avoid the sqrt call that Vector2.Distance would incur in a tight drag-frame path. The threshold is set to half a cell so a piece snaps only when its anchor is visually close to a vertex.

6.4 Occupancy validation

Placement is valid only if every triangle the piece would occupy is both in-bounds and currently unoccupied: 

foreach (var tri in piece.Data.TriangleOffsets)
{
    int boardCol = anchorVertex.Col + tri.dcol;
    int boardRow = anchorVertex.Row + tri.drow;
    if (out-of-bounds)               return false;
    if (_occupiedTriangles[r, c, t]) return false;
    targets.Add((boardRow, boardCol, tri.type));
}

Occupancy is tracked in a bool[N, N, 2] 3-D array for O(1) reads/writes. A parallel Dictionary<PieceBehaviour, List<(r,c,t)>> stores the reverse mapping so that lifting a piece (undoing placement) is also O(number of triangles in the piece) without scanning the entire occupancy array.

7 — Piece Rendering: Triangle Sprites

Each piece is visually composed of individual triangle sprites — one child GameObject per triangle in the region. This allows the tangram-style diagonal cut aesthetic without polygon mesh generation at runtime.

7.1 Shared sprite atlas

Only two Sprite objects exist for triangles across the entire runtime — one for type 0 (lower, ◸) and one for type 1 (upper, ◿). They are created once as static fields and re-used by every piece instance. Each triangle child uses MaterialPropertyBlock to tint the sprite to its piece colour, so all triangles share the same material with no GPU draw-call overhead.

7.2 Procedurally generated triangle textures

The two triangle sprites are generated from code via CPU pixel writes into a 64×64 Texture2D. The mask function relies on a simple linear inequality: 

// type 0 (lower): pixel is inside the triangle if x > y
float edge  = (type == 0) ? (x - y) : (y - x);
float alpha = Clamp01(edge + 1.0f);   // +1 px soft anti-alias fringe

The +1.0f offset produces a one-pixel soft edge that eliminates aliasing on the diagonal without a separate anti-aliasing pass.

7.3 Polygon collider

PieceBehaviour.BuildCollider assigns one path per triangle to the piece's PolygonCollider2D. Each path is a three-vertex array computed in local space from the triangle's (dcol, drow, type) offset: 

// type 0 (lower): BL, BR, TR
path = { (x0, y0), (x1, y0), (x1, y1) };
// type 1 (upper): BL, TR, TL
path = { (x0, y0), (x1, y1), (x0, y1) };

The multi-path PolygonCollider2D is Unity's recommended approach for non-convex shapes — it handles input raycasting and physics correctly with no extra work.

8 — Snap-Dot Visual Hint System

When the player begins dragging a piece, glowing dots appear on its surface. These dots mark interior vertices — grid vertices shared by many of the piece's own triangles — hinting to the player where the natural snap anchor points are.

8.1 Interior vertex scoring

Each grid vertex can be surrounded by up to 6 triangles (3 lower-type + 3 upper-type). A vertex's interior score is how many of those 6 surrounding triangles belong to the current piece. The lookup is a hard-coded 6-case test against a HashSet of the piece's (dcol, drow, type) tuples: 

// lower-type triangles touching vertex (vCol, vRow):
if (triSet.Contains((vCol,     vRow,     0))) n++;   // BL vertex of this lower tri
if (triSet.Contains((vCol - 1, vRow,     0))) n++;   // BR vertex of left lower tri
if (triSet.Contains((vCol - 1, vRow - 1, 0))) n++;   // TR vertex of lower-left lower tri
// upper-type:
if (triSet.Contains((vCol,     vRow,     1))) n++;
if (triSet.Contains((vCol - 1, vRow - 1, 1))) n++;
if (triSet.Contains((vCol,     vRow - 1, 1))) n++;

8.2 Step-down threshold selection

Candidate vertices are selected by descending through thresholds [6, 4, 2, 0] and picking the highest threshold that yields at least one candidate. This ensures that even single-triangle pieces (which have no interior vertex with count ≥ 2) always get at least one dot.

8.3 Weighted dot count

The number of dots per piece is drawn from a weighted distribution to keep the visual from feeling mechanical:

ProbabilityNumber of dots
80 %1
12 %2
5 %3
3 %4

Candidate vertices are Fisher-Yates-shuffled and then the first dotCount are selected. Dots fade in/out smoothly using DOTween when the drag state changes.

12 — Algorithms & Prior Art

The implementation draws from several established techniques:

  • Randomised BFS / Prim's region-growing — the canonical algorithm for procedurally partitioning a grid into irregular connected regions, widely used in roguelike dungeon generators. Our carver is a direct application on a triangular adjacency graph rather than a square grid.
  • Fisher-Yates shuffle — used three times: neighbour-list shuffling inside BFS (piece shape randomisation), colour-palette shuffling (visual diversity per level), and snap-dot candidate shuffling (visual variety). The standard Knuth/Durstenfeld in-place variant is used throughout.
  • Greedy smallest-first merge — a heuristic for balancing a partition under a cardinality constraint, analogous to Huffman-coding's repeated minimal-pair merges, but applied spatially rather than by frequency weight.
  • Lazy centroid cache with reference-equality keying — a common optimisation for deferred computation of geometric aggregates in spatial data structures; identical in spirit to the memo-table pattern in dynamic programming.
  • Squared-distance threshold test — avoiding sqrt in hot paths is a standard micro-optimisation in game engine code (see any game-math reference, e.g. Game Programming Gems Vol. 1, Section 1.1).
